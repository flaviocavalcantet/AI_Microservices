ARCHITECTURE DESIGN:
─────────────────────────────────────────────────────────────────────────────

ROLES:
  • admin   - Full system access, manages other users
  • user    - Standard authenticated user, basic operations
  • worker  - Service-to-service, limited scope

JWT CLAIMS:
  iss             - Issuer (auth_service)
  aud             - Audience (ai_platform)
  sub             - User ID
  iat             - Issued at
  exp             - Expiration time
  jti             - Unique token ID
  roles           - User roles [ADMIN, USER, WORKER]
  email           - User email
  session_id      - Session family identifier
  provider        - OAuth provider (optional)
  display_name    - User display name (optional)
  avatar_url      - User avatar URL (optional)

SIGNING STRATEGIES:
  Development:  HS256 (HMAC - symmetric key)
  Production:   RS256 (RSA - public/private key)

REQUEST FLOW:
  1. Client sends request with Authorization header
  2. Middleware extracts Bearer token
  3. JWTHandler validates signature and claims
  4. AuthContext injected into g.auth_context
  5. Route decorators check authorization
  6. Route handler executes with auth context
  7. Response returned

AUTHORIZATION LAYERS:
  • JWT Validation (signature, expiration, claims)
  • Role-Based Access Control (is user in required role?)
  • Resource Ownership (does user own this resource?)
  • Custom Policies (quota, department, time-based, etc.)
  • Composable Policies (AND/OR combinations)
